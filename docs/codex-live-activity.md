# Codex live activity

This page is for contributors. It lists how OpenOrc shows each item and notification from the `codex app-server` protocol while Codex works. Last verified against `codex-cli` 0.154.0. To compare another release, generate its bindings with `codex app-server generate-ts --out <directory>` and check `v2/ThreadItem.ts`, `ServerNotification.ts`, and the notification types they reference. The adapter opts into the app-server's experimental API when it starts.

## Item inventory

All 19 `ThreadItem` variants have an intentional projection. Item IDs determine row identity and first arrival determines order. Completion updates the same row.

| Provider item                           | Visible representation and available progress                                                                                                                                                                                                                           |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `userMessage`                           | The host records accepted input as a user message; the native echo does not duplicate it.                                                                                                                                                                               |
| `agentMessage`                          | “Writing response” on an empty start; normal assistant text deltas; final text replaces the draft.                                                                                                                                                                      |
| `reasoning`                             | “Thinking” on start, including empty summaries. Available summary paragraphs stream, then final summaries reconcile in place. Completion ends the indicator without requiring another item.                                                                             |
| `commandExecution`                      | Shell row with command/cwd, running state, incremental stdout/stderr in the expanded row, terminal input progress, aggregate output and terminal state.                                                                                                                 |
| `fileChange`                            | Patch row with live output, updated file/diff details, and terminal state.                                                                                                                                                                                              |
| `mcpToolCall`                           | Named tool row with arguments, provider progress messages, result/error and terminal state.                                                                                                                                                                             |
| `dynamicToolCall`                       | Named tool row with arguments, exposed content items, success/failure. The integration does not register client-executed dynamic tools; unexpected execution requests receive an unsupported-method error.                                                              |
| `plan`                                  | Planning activity, incremental plan text and final snapshot.                                                                                                                                                                                                            |
| `webSearch`                             | Search activity, query and inspectable action/results (including page open/find actions).                                                                                                                                                                               |
| `collabAgentToolCall`                   | Delegation call activity with tool, prompt, receiver IDs and exposed agent states/messages. Completion describes the call; it does not assert that a spawned agent has finished its assignment.                                                                         |
| `subAgentActivity`                      | Provider agent path and activity kind, with inspectable thread identity.                                                                                                                                                                                                |
| `imageView`                             | Image-view activity and path.                                                                                                                                                                                                                                           |
| `imageGeneration`                       | Typed image-generation activity, live composer status, inline saved-image preview, prompt and failure details. Binary/base64 results are not rendered; the provider log keeps a truncated copy. Click previews or local Markdown image links to open the thread viewer. |
| `sleep`                                 | Waiting activity with requested duration in details.                                                                                                                                                                                                                    |
| `enteredReviewMode`, `exitedReviewMode` | Review transition activity and review description.                                                                                                                                                                                                                      |
| `hookPrompt`                            | Hook context activity with exposed fragments.                                                                                                                                                                                                                           |
| `functionCallOutput`                    | Named tool-output activity with the provider's exposed output body.                                                                                                                                                                                                     |
| `contextCompaction`                     | Dedicated compaction activity managed by the adapter's maintenance controller; see below.                                                                                                                                                                               |

Future unknown **items** get an inspectable “Codex activity: <type>” row. Unknown transport notifications do not create agent-work rows.

Codex's five server requests (command approval, file-change approval, permission approval, user input, and MCP elicitation) show as approval or question cards. An MCP elicitation form is not shown field by field: when you allow it, OpenOrc fills the form with defaults (yes for yes/no fields, the first choice for lists, and otherwise the field's default, or 0 or an empty string). A form with no fields from OpenOrc's own connection is accepted without a card. Showing live activity adds no tool-execution ability or approval policy.

## Lifecycle and replay guarantees

- Manual compaction appears when requested, before RPC acceptance or item start. RPC acceptance is not completion. Its turn determines success, failure or interruption. Concurrent requests still coalesce.
- Automatic compaction appears at item start and completes at item completion, with turn termination as a fallback. Repeated automatic compaction items can each appear during the same turn.
- Input keeps waiting on the adapter's maintenance promise until the compact turn ends. Failures, interruption and process exit reject held input; a late legacy completion cannot block a subsequent message.
- Tool output deltas append. A non-null final aggregate replaces that stream instead of appending it; absent aggregates retain the stream. Expanded output is scrollable and is not truncated by the renderer. Provider-side truncation cannot be recovered.
- Turn/session terminal events and fatal errors close active tools, reasoning, other activities, assistant streaming, and pending approval indicators. For providers without an explicit reasoning lifecycle, the thinking indicator ends when the next event arrives.
- Host event IDs are shared by live frames and persisted events. Hydration ignores overlapping event IDs, preserving identical legitimate chunks with distinct IDs. History retrieval without an explicit limit includes the full run, including its terminal events beyond 5,000 events.
- Recovery writes a terminal event for sessions the previous app instance left open, so replay can close them too. New event fields are optional for old ledgers. Old ledgers cannot gain steps that an older adapter never normalized; their native notifications stay in the provider log for investigation until it expires.
- The provider may supply no reasoning summary, no delegated-agent message, or no intermediate output for a given activity. The UI shows lifecycle and exposed details without inventing text.

## Verification

`apps/desktop/src/renderer/src/lib/codex-activity.test.ts` drives the real `CodexAdapter`, `StdioJsonRpc`, shared event validator and renderer `applyFrame`/`getRun`. It covers these items: `agentMessage` (including empty starts), `reasoning` (with and without summaries), `commandExecution` (including terminal input), `fileChange` (including patch updates), `mcpToolCall` and `dynamicToolCall` (progress and failures), `plan`, `webSearch`, `imageGeneration` (including its saved preview), and `contextCompaction` (and its input barrier). It also covers hooks, automatic approval review, connection recovery, plan and diff snapshots, terminal states, approval resolution, a real SQLite `LedgerWriter`/`listEvents` replay including artifact payloads, conversation switching, and overlapping history and live delivery. The other nine item types have no dedicated test here.

Run these commands from the repository root:

```sh
pnpm --filter @openorc/agents test
pnpm --filter @openorc/desktop test
pnpm --filter @openorc/db test
pnpm --filter @openorc/core test
pnpm -r typecheck
```

These checks use scripted provider processes and do not call Codex models. The core suite needs localhost permission for its fixture MCP server.

Local image links, generated-image previews and the thread image viewer are described in [appearance and rich thread output](appearance-rich-output.md#links-and-images-in-threads).
